# Lab 3 API Contract — Authentication, Roles, IT Staff Ticketing and Administration

Extends [docs/lab-02/api-spec.md](../lab-02/api-spec.md). Lab 2 endpoints keep their paths and their
bodies; what changes is how identity arrives. Business rules referenced as BR-nn are in
[specification.md](specification.md) §5.

Base URL: `http://localhost:3000`. Every request and response body is JSON, except the attachment
upload (multipart) and the attachment download (binary).

---

## 1. Authentication mechanism

### 1.1 Session cookie

| Property | Value |
|---|---|
| Cookie name | `toktickit_session` |
| Value | 32 random bytes, hex encoded, generated by `crypto.randomBytes` |
| Flags | `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=28800` (8 hours), `Secure` when `NODE_ENV=production` |
| Storage | One row in `Session` with `id`, `userId`, `createdAt`, `expiresAt` |
| Invalidation | `POST /api/auth/logout` deletes the row; an expired row is treated as absent (BR-07) |

The cookie is set by `POST /api/auth/login` and cleared by `POST /api/auth/logout`. Client JavaScript
never reads it. The browser sends it automatically; the client fetch wrapper therefore uses
`credentials: "include"`, and the server sets `Access-Control-Allow-Credentials: true` with an
explicit `origin` (no wildcard) from `CLIENT_ORIGIN`.

The Lab 2 `X-Requester-Id` header is removed. If a client sends it, or sends `requesterId` in a body,
the value is ignored (BR-19).

### 1.2 Resolution order on every protected endpoint

1. No cookie, unknown session, or expired session → **401** `{"error":"Authentication required"}`.
2. Session found but the user is inactive → **401** and the session row is deleted (BR-10).
3. `mustChangePassword` is true and the path is not `/api/auth/me`, `/api/auth/password` or
   `/api/auth/logout` → **403** `{"error":"Password change required","code":"PASSWORD_CHANGE_REQUIRED"}` (BR-02).
4. Role not permitted for the endpoint → **403** `{"error":"You do not have access to this resource"}`.
5. Resource not owned by the caller, where ownership applies → **404**, identical to a missing
   resource (BR-22).

### 1.3 Error shape

```json
{ "error": "Validation failed", "fields": [{ "field": "email", "message": "Enter a valid email address" }] }
```

`fields` is present only for 400 validation failures. `code` is present only where a client must
branch on it: `PASSWORD_CHANGE_REQUIRED`, `EMAIL_IN_USE`, `LAST_ADMINISTRATOR`, `SELF_DEACTIVATION`,
`INVALID_TRANSITION`, `ATTACHMENT_REMOVED`.

### 1.4 Status codes in use

| Code | Meaning |
|---|---|
| 200 | Success with a body |
| 201 | A resource was created |
| 204 | Success with no body (logout, attachment removal) |
| 400 | Validation failure, including an invalid status transition |
| 401 | Not authenticated, or the session is gone, expired or belongs to a deactivated user |
| 403 | Authenticated but not permitted, including the forced password change |
| 404 | Not found, or found but not the caller's to see |
| 409 | Conflict: duplicate email, duplicate ticket submission |
| 410 | The attachment was removed (Lab 2) |
| 413 | The uploaded file is larger than 5 MB (Lab 2) |
| 500 | Unexpected server error, with a safe message |

## 2. Authorization matrix

R = Requester, S = IT Staff, A = Administrator. "own" means the row must belong to the caller.

| Endpoint | R | S | A |
|---|---|---|---|
| `POST /api/auth/login` | public | public | public |
| `POST /api/auth/logout`, `GET /api/auth/me`, `POST /api/auth/password` | ✔ | ✔ | ✔ |
| `GET /api/health` | public | public | public |
| `GET /api/categories`, `GET /api/related-systems` | ✔ | ✔ | ✔ |
| `POST /api/tickets` | ✔ | ✖ | ✖ |
| `GET /api/tickets`, `GET /api/tickets/:id` | own | ✖ | ✖ |
| `POST /api/tickets/:id/attachments`, `GET /api/tickets/:id/attachments` | own | ✖ | ✖ |
| `PATCH /api/attachments/:id/remove` | own | ✖ | ✖ |
| `GET /api/attachments/:id/download` | own | ✔ | ✔ |
| `GET /api/tickets/:id/comments` | own | ✔ | ✔ |
| `POST /api/tickets/:id/comments` | own | ✔ | ✔ |
| `POST /api/tickets/:id/problem-resolved` | own | ✖ | ✖ |
| `GET /api/tickets/:id/notes`, `POST /api/tickets/:id/notes` | ✖ 404 | ✔ | ✔ |
| `GET /api/staff/tickets`, `GET /api/staff/tickets/:id` | ✖ | ✔ | ✔ |
| `PATCH /api/staff/tickets/:id/owner`, `PATCH /api/staff/tickets/:id` | ✖ | ✔ | ✖ |
| `GET/POST /api/admin/users`, `PATCH /api/admin/users/:id`, `POST /api/admin/users/:id/password` | ✖ | ✖ | ✔ |

✖ returns 403, except the Internal Note endpoints, which return **404** to a Requester so that the
existence of notes on a ticket is not disclosed (BR-22, AC-14).

## 3. Authentication endpoints

### 3.1 `POST /api/auth/login`

Public. Request:

```json
{ "email": "napat.sri@kmutt.ac.th", "password": "ChangeMe!2026" }
```

Validation: `email` required, trimmed, lower-cased, valid syntax; `password` required, 1..128
characters (the password *rules* apply when setting a password, not when supplying one).

**200**

```json
{
  "user": { "id": 1, "name": "Napat Srisai", "email": "napat.sri@kmutt.ac.th",
            "role": "REQUESTER", "mustChangePassword": true }
}
```

Sets `toktickit_session`. `lastLoginAt` is updated.

| Failure | Code | Body |
|---|---|---|
| Missing or malformed field | 400 | `{"error":"Validation failed","fields":[…]}` |
| Unknown email or wrong password | 401 | `{"error":"Invalid email or password. Please try again."}` (identical in both cases, BR-04) |
| Correct password, inactive account | 403 | `{"error":"This account is not active. Please contact an administrator."}` (BR-05; no session is created) |

### 3.2 `POST /api/auth/logout`

Any authenticated user. No body. **204**, session row deleted, cookie cleared. Calling it without a
session also returns 204, so a client can log out defensively.

### 3.3 `GET /api/auth/me`

Any authenticated user, and reachable while `mustChangePassword` is true.

**200**

```json
{
  "user": { "id": 7, "name": "Warin Chaiyaporn", "email": "warin.cha@kmutt.ac.th",
            "role": "IT_STAFF", "mustChangePassword": false, "lastLoginAt": "2026-09-18T03:11:02.000Z" }
}
```

No password material appears in the body (AC-06). **401** when there is no valid session.

### 3.4 `POST /api/auth/password`

Any authenticated user, and reachable while `mustChangePassword` is true.

```json
{ "currentPassword": "ChangeMe!2026", "newPassword": "Kmutt#2026x", "confirmPassword": "Kmutt#2026x" }
```

Validation (BR-12, BR-13, BR-14): `newPassword` 8..128 characters with an upper-case letter, a
lower-case letter, a digit and a special character; `confirmPassword` must match; `newPassword` must
differ from `currentPassword`.

**200** returns the same shape as `GET /api/auth/me` with `mustChangePassword: false`. The current
session stays valid (BR-15).

| Failure | Code | Body |
|---|---|---|
| Rule violation or mismatch | 400 | `fields` names `newPassword` or `confirmPassword` |
| Wrong current password | 400 | `fields` names `currentPassword` with "Your current password is not correct" |

## 4. Reference and Requester endpoints (Lab 2, re-identified)

`GET /api/categories` and `GET /api/related-systems` are unchanged except that they now require a
session. `GET /api/requesters` is **removed**; requesting it returns 404 (BR-61).

`POST /api/tickets`, `GET /api/tickets`, `GET /api/tickets/:id`, the three attachment endpoints and
the attachment download keep the request and response shapes defined in the Lab 2 contract, with
three changes:

1. The requester is the authenticated user. Any `requesterId` in a body or header is ignored (BR-18).
2. Every ticket response gains `itPriority`, `owner` and the resolution fields:

```json
{
  "id": 42, "ticketNumber": "TKT-2026-000042", "status": "IN_PROGRESS",
  "requestedPriority": "HIGH", "itPriority": "MEDIUM",
  "summary": "Cannot connect to VPN", "description": "…",
  "requester": { "id": 1, "name": "Napat Srisai" },
  "owner": { "id": 7, "name": "Warin Chaiyaporn" },
  "category": { "id": 4, "name": "Network" },
  "relatedSystem": { "id": 3, "name": "VPN" },
  "resolutionSummary": null,
  "requesterResolvedAt": null,
  "createdAt": "2026-09-10T02:14:55.000Z", "updatedAt": "2026-09-12T08:02:11.000Z"
}
```

`owner` is `null` for an unassigned Ticket (AC-31).

3. `GET /api/attachments/:id/download` additionally permits IT Staff and Administrators, because they
   must be able to see what the Requester attached. Removal stays Requester-only.

### 4.1 `GET /api/tickets/:id/comments`

Requester (own ticket), IT Staff, Administrator. **200**

```json
{
  "comments": [
    { "id": 12, "body": "We are investigating the issue on your device.",
      "author": { "id": 7, "name": "Warin Chaiyaporn", "role": "IT_STAFF" },
      "createdAt": "2026-09-12T03:30:00.000Z" }
  ]
}
```

Ordered by `createdAt` ascending. A Requester asking about a Ticket that is not theirs receives 404.

### 4.2 `POST /api/tickets/:id/comments`

Same roles. Request `{ "body": "Thanks, that fixed it." }`.

Validation: `body` required, trimmed, 1..2000 characters (BR-45). **201** returns the created comment
in the shape above. **400** for empty, whitespace-only or over-length content. The author and the
timestamp come from the backend (BR-44).

### 4.3 `POST /api/tickets/:id/problem-resolved`

Requester, own Ticket only. No body.

**200** returns the updated ticket with `requesterResolvedAt` set to the backend time. The status is
**not** changed (BR-40, AC-23). Calling it twice is idempotent: the first timestamp is kept and 200 is
returned. Any other role receives 403; another Requester's Ticket receives 404.

## 5. Internal Notes

### 5.1 `GET /api/tickets/:id/notes`

IT Staff and Administrator only. **200**

```json
{
  "notes": [
    { "id": 4, "body": "Router firmware on floor 3 is out of date; raised with network team.",
      "author": { "id": 8, "name": "Pimchanok Rattana", "role": "IT_STAFF" },
      "createdAt": "2026-09-12T04:02:00.000Z" }
  ]
}
```

A Requester receives **404** with `{"error":"Ticket not found"}` — never 403, and never any note
content (AC-14).

### 5.2 `POST /api/tickets/:id/notes`

IT Staff and Administrator only. Request `{ "body": "…" }`, validated exactly as a Public Comment.
**201** returns the created note. A Requester receives 404.

## 6. IT Staff queue and ticket operations

### 6.1 `GET /api/staff/tickets`

IT Staff and Administrator.

| Parameter | Values | Default | Invalid value |
|---|---|---|---|
| `search` | free text, matched case-insensitively against `ticketNumber` and `summary`, trimmed, ≤ 120 chars | none | ignored when empty |
| `status` | one of the eight statuses, repeatable | all | 400 |
| `categoryId` | integer | all | 400 |
| `itPriority` | `LOW`, `MEDIUM`, `HIGH`, `URGENT` | all | 400 |
| `ownerId` | integer, or the literal `unassigned` | all | 400 |
| `sort` | `createdAt`, `updatedAt`, `ticketNumber`, `itPriority`, `status` | `createdAt` | falls back to the default (AC-28) |
| `order` | `asc`, `desc` | `desc` | falls back to the default |
| `page` | integer ≥ 1 | 1 | falls back to 1 |
| `pageSize` | 10, 20 or 50 | 10 | falls back to 10 |

An unknown enum value in `status`, `itPriority`, `categoryId` or `ownerId` is a client error and
answers 400, because silently ignoring it would show the wrong work. An unknown `sort`, `order`,
`page` or `pageSize` only affects presentation, so it falls back to the default rather than failing a
queue a person is waiting on. `itPriority` sorts by severity, not alphabetically, with `createdAt` as
the tie-breaker.

**200**

```json
{
  "tickets": [ { "id": 42, "ticketNumber": "TKT-2026-000042", "summary": "Cannot connect to VPN",
                 "category": { "id": 4, "name": "Network" },
                 "requester": { "id": 1, "name": "Napat Srisai" },
                 "owner": null,
                 "requestedPriority": "HIGH", "itPriority": "HIGH", "status": "NEW",
                 "requesterResolvedAt": null,
                 "createdAt": "2026-09-10T02:14:55.000Z", "updatedAt": "2026-09-10T02:14:55.000Z" } ],
  "page": 1, "pageSize": 10, "totalItems": 37, "totalPages": 4
}
```

A Requester receives 403.

### 6.2 `GET /api/staff/tickets/:id`

IT Staff and Administrator. **200** returns the full ticket object from §4, plus `attachments` in the
Lab 2 shape, `comments` and `notes`. **404** when the Ticket does not exist.

### 6.3 `PATCH /api/staff/tickets/:id/owner`

IT Staff only (BR-24, D-10).

```json
{ "ownerId": 7 }
```

`ownerId` is an integer to assign or claim, or `null` to release the Ticket to unassigned. Claiming is
assigning oneself; there is no separate endpoint.

**200** returns the updated ticket.

| Failure | Code | Detail |
|---|---|---|
| `ownerId` is not an integer or `null` | 400 | field `ownerId` |
| The user does not exist, is inactive, or is not IT Staff | 400 | `{"error":"Validation failed","fields":[{"field":"ownerId","message":"Select an active IT Staff user"}]}` (BR-29) |
| Administrator caller | 403 | — |
| Unknown ticket | 404 | — |

### 6.4 `PATCH /api/staff/tickets/:id`

IT Staff only. Any subset of the three fields may be sent; an empty body is a 400.

```json
{ "itPriority": "MEDIUM", "status": "RESOLVED", "resolutionSummary": "Re-enrolled the VPN certificate." }
```

- `itPriority` — one of the four values (BR-31). The Requested Priority is never touched (BR-30).
- `status` — must be permitted from the Ticket's current status by the matrix in specification.md
  §5.1. Otherwise **400** with `code: "INVALID_TRANSITION"` and a message naming the current status;
  the Ticket is left unchanged (BR-36).
- `resolutionSummary` — required and non-empty when the target status is `RESOLVED`, 1..2000
  characters (BR-37). Sending it without a status simply updates the summary.
- `RESOLVED` sets `resolvedAt`; `CLOSED` sets `closedAt`; `REOPENED` clears `resolvedAt`. The
  confirmation required before Closed and Cancelled is a UI obligation (BR-39); the API accepts the
  transition on its own.

**200** returns the updated ticket. A Requester or an Administrator receives 403.

## 7. Administrator user management

All four endpoints require the Administrator role; every other role receives 403 (AC-16).

### 7.1 `GET /api/admin/users`

| Parameter | Values | Default |
|---|---|---|
| `search` | free text matched case-insensitively against name and email, ≤ 120 chars | none |
| `role` | `REQUESTER`, `IT_STAFF`, `ADMINISTRATOR` | all roles |

Unknown `role` → 400. The list is always sorted by name ascending and is not paginated (BR-57).

**200**

```json
{
  "users": [
    { "id": 9, "name": "Anong Sukjai", "email": "anong.suk@kmutt.ac.th", "role": "ADMINISTRATOR",
      "isActive": true, "mustChangePassword": false, "createdAt": "2026-09-01T04:00:00.000Z" }
  ]
}
```

No hash and no password field is ever returned.

### 7.2 `POST /api/admin/users`

```json
{ "name": "Alex Thompson", "email": "alex.thompson@kmutt.ac.th",
  "role": "IT_STAFF", "isActive": true, "initialPassword": "Start#2026" }
```

Validation: `name` 2..120 after trimming; `email` valid, ≤ 200, lower-cased; `role` one of the three;
`isActive` boolean, default true; `initialPassword` must satisfy the password rules (BR-12).

**201** returns the created user in the §7.1 shape with `mustChangePassword: true` (BR-51).

| Failure | Code | Body |
|---|---|---|
| Validation | 400 | `fields` |
| Email already used | 409 | `{"error":"That email address is already in use","code":"EMAIL_IN_USE"}` (BR-49) |

### 7.3 `PATCH /api/admin/users/:id`

Any subset of `name`, `email`, `role`, `isActive`. An empty body is a 400. The password is never
touched here (BR-55).

**200** returns the updated user.

| Failure | Code | Body |
|---|---|---|
| Validation | 400 | `fields` |
| Email already used by another user | 409 | `code: "EMAIL_IN_USE"` |
| Deactivating oneself | 400 | `{"error":"You cannot deactivate your own account","code":"SELF_DEACTIVATION"}` (BR-52) |
| Deactivating, or changing the role of, the last active Administrator | 400 | `{"error":"At least one active Administrator must remain","code":"LAST_ADMINISTRATOR"}` (BR-53) |
| Unknown user | 404 | — |

### 7.4 `POST /api/admin/users/:id/password`

```json
{ "initialPassword": "Reset#2026" }
```

Validated by the password rules. **200** returns the user with `mustChangePassword: true`. Every
existing session of that user is deleted, so a password reset takes effect immediately (BR-16,
AC-47). No other field changes.

## 8. Contract decisions

| ID | Decision | Reason |
|---|---|---|
| C-01 | A session cookie rather than an `Authorization: Bearer` header. | The browser sends it automatically and JavaScript cannot read it, which removes a whole class of token-leak bugs from the client code. |
| C-02 | The forced password change is enforced by a middleware that allows only `me`, `password` and `logout`. | The rule then holds for every endpoint, including ones added after this document, instead of being repeated per route (BR-02). |
| C-03 | Internal Note endpoints answer 404 to a Requester while staff endpoints answer 403. | 403 on a queue endpoint tells a Requester nothing they do not already know; 403 on a note endpoint would confirm that notes exist on their ticket. |
| C-04 | Invalid filter values fail with 400, invalid sort and paging values fall back to defaults. | A wrong filter changes which work is shown and must be loud; a wrong sort order only changes the order and must not block the queue. |
| C-05 | `PATCH …/owner` is separate from `PATCH …/:id`. | Ownership is the one operation whose audit story differs from field edits, and separating it keeps the validation for "must be an active IT Staff user" out of the general update path. |
| C-06 | Setting a new initial password deletes that user's sessions. | Otherwise an account whose password was just reset would stay signed in on another machine, which is the opposite of what the Administrator intended. |
