## 1. Sprint Goal

Deliver the Requester-facing half of TokTickIT: a person can pick a Development Requester identity,
raise an IT support ticket with attachments, receive an official ticket number generated by the
backend, then find, search, filter, sort and page through their own tickets, open one, and manage its
attachments — all in a consistent, responsive Zen Green interface, with one Requester never able to
see another Requester's data.

## 2. Stakeholder Request Interpretation

The IT department wants to start accepting real requests, so the Requester experience must be
complete and trustworthy before any IT Staff tooling exists. Everything a Requester touches —
creating, finding, reading, and attaching evidence to a ticket — must work end to end against
PostgreSQL, with the ticket number and stored values coming from the backend rather than the browser.

Because authentication lands in Lab 3, the sprint substitutes a **Development Requester selector**: a
screen that lists seeded active requesters and lets the tester adopt one identity for the session.
This is a testing mechanism, not a login, and the specification treats it as such everywhere — the
selected identity is client-supplied and trusted only because Lab 2 has no attacker model yet.

The visual half of the request matters as much as the functional half: this sprint fixes the Zen
Green design language and the reusable form, list, badge, validation, loading, empty, error and
responsive conventions that Labs 3 and 4 must reuse instead of reinventing.

## 3. Scope

### 3.1 Included

- Development Requester selection, display, switching, and requester-scoped data reloading.
- Create Ticket: form, validation, backend-generated ticket number, attachments at creation.
- My Tickets: requester-owned paginated list with search, filters, sorting, and all list states.
- Requester Ticket Detail: read-only ticket view.
- Attachment lifecycle: upload, metadata, download, soft removal with reason.
- Ownership protection enforced in the backend for tickets and attachments.
- Zen Green theme, reusable UI components, responsive desktop/tablet/mobile layouts.
- Automated unit, API, UI, UI-style, responsive, and E2E tests plus visual evidence.

### 3.2 Explicitly excluded

- Authentication and security: login, logout, passwords, hashing, sessions, tokens, real role-based
  authorization. The Development Requester selector is **not** authentication.
- IT Staff workflow: staff dashboard/queue, claiming or reassigning tickets, IT Priority, owner
  functions.
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken.
- Ticket lifecycle beyond the initial `NEW` status: resolving, closing, reopening, cancelling,
  resolution confirmation.
- Administration: user, requester, role, and reference-data management screens.

## 5. Business Rules

### Ticket defaults and system-generated values

| ID | Rule |
|---|---|
| BR-01 | The official Ticket Number is generated by the backend and is unique across the database. Its format is `TKT-<YYYY>-<6-digit zero-padded sequence>`, e.g. `TKT-2026-000042`. The client never supplies or guesses it. |
| BR-02 | A new Ticket begins with Current Status `NEW`. No other status transition exists in Lab 2. |
| BR-03 | Ticket Date is the server's creation timestamp (`createdAt`); `updatedAt` is maintained by the database on every write. |
| BR-04 | Ticket Number, Ticket Date, Requester, and Current Status are read-only in the UI at all times. |

### Requester selection and switching

| ID | Rule |
|---|---|
| BR-05 | Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication; Lab 3 replaces it with a real authenticated identity. |
| BR-06 | Only active Requesters appear in the selector. An inactive Requester is never selectable and never returned by the active-requester endpoint. |
| BR-07 | The selection is stored client-side in `localStorage` under `toktickit.requesterId` and sent to the backend on every request via the `X-Requester-Id` header. |
| BR-08 | Changing the Requester clears all requester-scoped state and reloads ticket data for the new identity. In-progress form input is discarded after an explicit confirmation. |
| BR-09 | If no Requester is selected, any ticket screen redirects to the Development Requester Selection screen. |
| BR-10 | If the stored Requester id no longer exists or has become inactive, the selection is cleared and the selector is shown again with an explanatory message. |

### Ownership

| ID | Rule |
|---|---|
| BR-11 | A Ticket belongs to exactly one Requester and that owner never changes in Lab 2. |
| BR-12 | The backend authorises every ticket and attachment operation against the `X-Requester-Id` header, never against a client-supplied ticket owner field. |
| BR-13 | A request for a Ticket or Attachment owned by another Requester is answered `404 Not Found`, identical to a request for a non-existent record, so that existence is not disclosed. |
| BR-14 | Ticket lists are always filtered by the selected Requester server-side; the client cannot widen the scope with a query parameter. |

### Validation and duplicate submission

| ID | Rule |
|---|---|
| BR-15 | Summary is required, trimmed before validation, and must be 10–120 characters. Description is required, trimmed, and must be 20–4000 characters. |
| BR-16 | Category, Related System, and Requested Priority are required. Category and Related System must reference an existing **active** row; Requested Priority must be one of `LOW`, `MEDIUM`, `HIGH`, `URGENT`. |
| BR-17 | The backend validates every field independently of the frontend and returns one message per offending field. Frontend validation is a convenience layer and never replaces the backend check. |
| BR-18 | The Submit action is disabled and shows a busy state while a submission is in flight, so a double click cannot create two tickets. |
| BR-19 | A second ticket with the same trimmed summary **and** description by the same Requester within 60 seconds is rejected with `409 Conflict` as a duplicate submission. |
| BR-20 | Validation failure never clears the form: all entered values, including the pending attachment selection, are preserved. |

### Search, filtering, sorting, pagination

| ID | Rule |
|---|---|
| BR-21 | Search matches, case-insensitively, any substring of Ticket Number or Summary. |
| BR-22 | Filters are category, related system, requested priority, and status; multiple filters combine with AND. |
| BR-23 | Sortable fields are `createdAt`, `updatedAt`, `ticketNumber`, and `requestedPriority`, each ascending or descending. The default sort is `createdAt` descending, with `id` descending as the deterministic secondary sort. |
| BR-24 | Pages are 1-based. Permitted page sizes are 5, 10, 20, and 50; the default is 10. |
| BR-25 | An invalid, unknown, or out-of-range query parameter is rejected with `400 Bad Request` and a message naming the parameter — it is never silently ignored. |
| BR-26 | Every list response carries `page`, `pageSize`, `totalItems`, and `totalPages` metadata. |
| BR-27 | Requesting a page beyond the last page returns `200` with an empty `items` array and correct metadata, not an error. |

### Failure behaviour and empty states

| ID | Rule |
|---|---|
| BR-28 | Unexpected server errors return a generic safe message and never expose stack traces, SQL, filesystem paths, or Prisma internals. |
| BR-29 | When an API call fails, the screen shows an explicit failure state with a retry affordance; a failed Create Ticket submission keeps every entered value (see BR-20). |
| BR-30 | The empty state ("you have no tickets yet") and the no-results state ("no tickets match these filters") are distinct, and the no-results state offers a Clear filters action. |

### Attachments

| ID | Rule |
|---|---|
| BR-31 | Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF, validated by extension **and** MIME type. |
| BR-32 | Maximum size is 5 MB (5 × 1024 × 1024 bytes) per file. |
| BR-33 | A Ticket may have at most five **active** attachments. Soft-removed attachments do not count toward the limit. |
| BR-34 | Stored metadata is: original filename, stored filename, MIME type, size in bytes, uploader Requester id, and upload timestamp. |
| BR-35 | The stored filename is a server-generated UUID plus the validated extension. The original filename is never used as a filesystem path, and files live outside the web root in `server/uploads/`, which is git-ignored. |
| BR-36 | Removal is always soft: `removedAt`, `removalReason`, and `removedByRequesterId` are set and the row is retained. No endpoint deletes an attachment row or its metadata. |
| BR-37 | Removal requires an explicit confirmation and a removal reason of 3–200 characters. |
| BR-38 | Only the owning Requester may upload to, download from, or remove an attachment of their own ticket. |
| BR-39 | A removed Attachment remains visible as metadata, is clearly marked Removed with its reason and timestamp, and cannot be downloaded or previewed — its download endpoint answers `410 Gone`. |
| BR-40 | An already-removed Attachment cannot be removed again (`409 Conflict`). |
| BR-41 | Attachment upload is independent of ticket creation: if the ticket is saved but an attachment upload fails, the ticket is kept, the failure is reported per file, and the Requester is invited to retry the upload from Ticket Detail. The ticket is never rolled back because of an attachment failure. |
| BR-42 | Each upload is written to disk first and recorded in the database in the same request; if the database write fails, the orphaned file is deleted so that storage and metadata cannot diverge. |

### Transition to real authentication

| ID | Rule |
|---|---|
| BR-43 | All identity handling is confined to one backend helper that resolves the current Requester from the `X-Requester-Id` header, so Lab 3 can replace it with a session or token lookup without touching route logic. |
| BR-44 | The Development Requester Selection screen is labelled as a Lab 2 testing mechanism in the UI itself, so it can never be mistaken for a login screen during demonstration or grading. |

## 6. UI Specification Summary

Full detail lives in [ui-spec.md](ui-spec.md); this section states the binding structure.

- **Application shell** — Zen Green header (`#006B3C`) carrying the TokTickIT identity, My Tickets and
  Create Ticket navigation with a clear active-page indicator, the selected Requester's name, and a
  Change Requester action. Navigation collapses to a mobile menu below 768 px.
- **Development Requester Selection** — title, the "this is not a login screen" explanation, a
  dropdown of active requesters loaded from PostgreSQL, a Continue button, and loading / empty /
  API-failure states.
- **Create Ticket** — read-only system fields (ticket number placeholder, ticket date, requester)
  visually distinct from editable fields; classification fields grouped; summary and description given
  full width; attachment picker below the main fields; primary Submit and secondary Cancel at the
  bottom. Labels sit above controls, required fields carry a red asterisk **and** a real validation
  message below the field, and Submit shows a busy state.
- **My Tickets** — search box, category / related system / priority / status filters, sort control,
  page-size control, a Create Ticket action, a desktop table (Ticket Number, Summary, Category,
  Related System, Priority, Status, Last Updated) and mobile cards carrying the same fields, plus
  pagination and the four list states.
- **Ticket Detail** — read-only ticket header grouped by identity / classification / content, then a
  clearly separated Attachments section with per-attachment state (Active, Uploading, Removed) and the
  Add, Download, and Remove actions.
- **States** — every screen implements initial, loading, success, validation, failure, and where
  applicable empty and no-results states.
- **Responsive** — desktop ≥ 992 px multi-column with a max content width; tablet 768–991 px
  two-column where practical; mobile < 768 px single column with touch-friendly controls and no
  horizontal page scrolling.
- **Badges** — Requested Priority and Current Status render as badges whose meaning is carried by text
  as well as colour.

## 7. Data Changes

### 7.1 Models

| Model | Fields |
|---|---|
| `RequesterUser` | `id` Int PK, `name` String, `email` String unique, `department` String?, `isActive` Boolean default `true`, `createdAt`, `updatedAt` |
| `Category` *(extended from Lab 1)* | `id` Int PK, `name` String unique, `isActive` Boolean default `true`, `createdAt` |
| `RelatedSystem` | `id` Int PK, `name` String unique, `isActive` Boolean default `true`, `createdAt` |
| `Ticket` | `id` Int PK, `ticketNumber` String unique, `requesterId` FK → `RequesterUser`, `categoryId` FK → `Category`, `relatedSystemId` FK → `RelatedSystem`, `summary` String, `description` String, `requestedPriority` `Priority`, `status` `TicketStatus` default `NEW`, `createdAt`, `updatedAt` |
| `Attachment` | `id` Int PK, `ticketId` FK → `Ticket`, `originalFilename` String, `storedFilename` String unique, `mimeType` String, `sizeBytes` Int, `uploadedByRequesterId` FK → `RequesterUser`, `uploadedAt`, `removedAt` DateTime?, `removalReason` String?, `removedByRequesterId` FK? → `RequesterUser` |

Enums: `Priority { LOW, MEDIUM, HIGH, URGENT }`, `TicketStatus { NEW }` — `TicketStatus` is
deliberately single-valued in Lab 2 (BR-02) and grows in Lab 3.

### 7.2 Relationships

- `RequesterUser 1 — n Ticket` (`Ticket.requesterId`, restrict on delete).
- `Ticket 1 — n Attachment` (`Attachment.ticketId`, cascade on delete of the ticket, which never
  happens in Lab 2).
- `Category 1 — n Ticket`, `RelatedSystem 1 — n Ticket` (restrict on delete: reference data in use
  cannot be deleted, only deactivated).
- `RequesterUser 1 — n Attachment` twice, as uploader and as remover, for the audit metadata BR-34 and
  BR-36 require.

### 7.3 Indexes and constraints

- Unique: `Ticket.ticketNumber` (BR-01), `RequesterUser.email`, `Category.name`,
  `RelatedSystem.name`, `Attachment.storedFilename`.
- Index `Ticket(requesterId, createdAt)` — **justified**: every My Tickets query filters by
  `requesterId` and the default sort is `createdAt` descending (BR-14, BR-23), so this composite index
  serves the filter and the sort with one index scan instead of a full table scan plus sort. It is the
  single hottest query path in the sprint.
- Index `Ticket(requesterId, status)` and `Ticket(requesterId, categoryId)` — support the most-used
  filter combinations without scanning a requester's whole history.
- Index `Attachment(ticketId, removedAt)` — the active-attachment count (BR-33) and the detail screen
  both read attachments of one ticket split by removal state.
- Soft removal is represented by nullable `removedAt` (plus reason and remover), never by a boolean
  alone, so that "when" and "why" are always recoverable.

### 7.4 Migration decisions

- One additive migration, `lab2_requester_ticketing`. Lab 1's `Category` table is altered, not
  dropped: `isActive` is added with default `true` so existing rows stay valid and the Lab 1
  `/api/categories` contract keeps working unchanged.
- No destructive column drops or renames, so the migration replays cleanly on a database seeded by
  Lab 1.
- Seed remains idempotent via `upsert` on the natural unique keys (BR: seed re-runs create no
  duplicates), and adds: 4 categories, ≥ 6 related systems, ≥ 4 active requesters, ≥ 1 inactive
  requester.

## 8. API Contract

Full request and response shapes, validation rules, and error cases are in [api-spec.md](api-spec.md).
Summary of the surface:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Lab 1 health check (unchanged) |
| GET | `/api/categories` | Active categories |
| GET | `/api/related-systems` | Active related systems |
| GET | `/api/requesters` | Active Development Requesters |
| POST | `/api/tickets` | Create one validated ticket for the selected Requester |
| GET | `/api/tickets` | Selected Requester's tickets — search, filter, sort, paginate |
| GET | `/api/tickets/:id` | One owned ticket with its attachments |
| POST | `/api/tickets/:id/attachments` | Upload one permitted attachment (multipart) |
| GET | `/api/tickets/:id/attachments` | Attachment metadata for one owned ticket |
| GET | `/api/attachments/:id/download` | Download an active attachment |
| PATCH | `/api/attachments/:id/remove` | Soft-remove an attachment with a reason |

Identity travels in the `X-Requester-Id` header (BR-07). Status codes in use: `200`, `201`, `400`,
`404`, `409`, `410`, `413`, `415`, `422`, `500` — each mapped to a concrete case in api-spec.md.

## 11. Assumptions and Decisions

| # | Decision | Rationale |
|---|---|---|
| D-01 | Identity is carried in an `X-Requester-Id` request header rather than a query parameter or body field. | Keeps the testing identity out of URLs and bodies so Lab 3 can swap the header for a session cookie or bearer token by changing one helper (BR-43). |
| D-02 | Cross-requester access answers `404`, not `403`. | A `403` confirms the record exists. `404` keeps the existence of another Requester's ticket private, which is the behaviour we want to keep after real auth arrives. |
| D-03 | The ticket number is derived from the row's own autoincrement id inside the creating transaction (`TKT-<year>-<id padded to 6>`). | Cannot collide, needs no counter table, and stays readable. The unique constraint is the final guard. |
| D-04 | Files are stored on the local filesystem in `server/uploads/` with UUID names, not in the database. | Keeps PostgreSQL small and matches how Lab 3/4 would move to object storage; UUID names neutralise path traversal and filename collisions (BR-35). |
| D-05 | Duplicate submission is detected by identical trimmed summary + description from the same Requester within 60 s. | Blocks the realistic double-submit accident without inventing an idempotency-key protocol that Lab 2's UI would not exercise. |
| D-06 | Attachment upload failures never roll back a successfully created ticket. | The ticket is the valuable artefact; forcing the Requester to retype it because one file failed would be worse than an incomplete attachment set (BR-41). |
| D-07 | `TicketStatus` is an enum with a single value in Lab 2. | Honest to the excluded scope while making the Lab 3 extension a pure enum addition rather than a type change. |
| D-08 | Page size is restricted to 5/10/20/50 instead of any integer. | Bounds the query cost and makes the invalid-parameter rule (BR-25) testable. |
| D-09 | The Lab 1 `/api/categories` response shape is preserved and only filtered to active rows. | The Lab 1 Supertest test stays green, so the Lab 2 migration cannot silently break the earlier contract. |
